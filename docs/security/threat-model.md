# QuantumShield Threat Model

Per Section 52. Scope: QuantumShield itself as a system (not the fictional
enterprise lab it simulates, whose threats are the *subject matter* the
platform analyzes, not a threat to the platform).

## Assets
- The relational inventory (assets, algorithms, certificates, risk
  assessments, migration plans) — integrity matters more than
  confidentiality here, since the lab data is synthetic, but a real
  deployment's inventory would be sensitive.
- User credentials and JWT signing key (`QS_SECRET_KEY`).
- Trained model artifacts (`backend/artifacts/models/`) and their metadata.
- Audit log integrity.
- The migration authorization boundary (who can trigger a plan/simulate
  action).

## Trust boundaries
1. **Unauthenticated → authenticated** at every `/api/v1/*` route except
   `/health` and `/auth/token`.
2. **Viewer → analyst/admin** at every state-changing route
   (`require_analyst`/`require_admin` in `app/api/deps.py`).
3. **Frontend (browser, untrusted client) → backend (trusted server)** —
   the frontend never computes a risk score, benchmark value, or
   recommendation client-side; it only renders what the API returns.
4. **Discovery scanner input (YAML config files) → database** — a
   malformed or adversarial config file should not corrupt the inventory
   beyond the single asset entry it describes.

## Threat actors considered
- An unauthenticated network attacker probing the API.
- An authenticated `viewer`-role user attempting to exceed their
  permissions (trigger a migration, read audit logs).
- A malicious or malformed cryptographic-inventory config file (Section 52:
  "poisoned cryptographic inventory").
- A supply-chain-compromised dependency (`cryptography`, `pqcrypto`,
  `qiskit`, npm packages).
- (Forward-looking, not currently applicable) A future LLM-assisted
  explanation layer being tricked via prompt injection into producing
  content that looks like an authorized instruction.

## Threats and mitigations

| Threat | Mitigation | Residual risk |
|---|---|---|
| Unauthenticated access to inventory/risk/migration data | JWT required on every route but `/health`, `/auth/token`; RBAC via `require_viewer/analyst/admin` | Token expiry/secret rotation is config-only, not automated |
| Privilege escalation (viewer triggers a migration) | Every state-changing route depends on `require_analyst` or stricter (`ADR-007`); covered by automated regression tests (`tests/test_api.py::test_viewer_can_read_but_not_trigger_scan`, `::test_admin_only_audit_log`) and re-verified live via role-based 403 checks during frontend verification | Coverage is per-representative-route (scan, audit), not exhaustively every one of the ~15 state-changing endpoints individually |
| Poisoned/malformed cryptographic inventory | `discovery/scanner.py` wraps per-asset parsing in a try/except that logs the error and continues, so one malformed entry can't abort or corrupt the rest of the scan; only local, explicitly-configured lab directories are scanned (Section 7) | No schema validation beyond what parsing naturally enforces; a config that parses but contains implausible values (e.g. negative key size) is not rejected |
| Incorrect algorithm classification | Centralized `AlgorithmRegistry` (`ADR-001`) means classification logic exists in one place, not scattered | No automated cross-check against an external authoritative algorithm database |
| AI hallucination / fabricated risk explanation | No generative LLM sits in this path; SHAP/coefficient attributions are computed directly from the trained model (`ADR-004`) | N/A currently — revisit if a future LLM-assisted layer is added |
| Prompt injection | No LLM currently processes untrusted input anywhere in the runtime path | N/A currently (see `ADR-007`'s explicit forward-looking note) |
| Unauthorized migration execution | RBAC (`ADR-007`) + audit logging (`app/api/audit.py` records actor/action/before/after) | Audit log itself has no tamper-evidence mechanism (no hash chaining/signing) |
| Tampered benchmark/quantum-lab data | All results are generated by real execution at request time, not cached/editable client input; benchmark/quantum run requests take only algorithm/iteration/qubit parameters, never a result value | A database-level attacker with write access could still directly edit stored results — no application-level integrity check (e.g. signing) on stored `BenchmarkRun`/`QuantumRun` rows |
| API abuse / rate limiting | Per-IP rate limiting via `slowapi` (`app/core/rate_limit.py`): a tight `10/minute` tier on `/auth/token` (brute-force protection) and a `30/minute` tier on the CPU-bound benchmark/quantum-lab endpoints, with a `300/minute` default elsewhere; enforced by `tests/test_rate_limit.py` against the real running app | In-memory limiter storage keyed by IP — a multi-process/multi-instance deployment would need a shared backend (e.g. Redis) for the limit to hold across instances; not implemented, since this is a single-process dev/lab deployment |
| Supply-chain compromise | Dependencies pinned to exact versions (`requirements.txt`, `package-lock.json`); `pip-audit` runs in CI on every push/PR; `npm audit --audit-level=high` now runs in the frontend CI job too | `npm audit` is non-blocking (`\|\| true`) so a finding doesn't fail CI outright — it surfaces in the CI log for manual triage rather than gating the build |
| Secret management | `QS_SECRET_KEY` read from environment; a startup validator (`app/core/config.py::_reject_insecure_defaults_outside_development`, `tests/test_config.py`) refuses to boot in any `QS_ENVIRONMENT` other than `development` while the secret still equals the publicly-known default, so a `docker-compose up` without an operator-set key fails fast at startup instead of silently signing JWTs with a secret published in this repo's own source; `docker-compose.yml` also requires `QS_SECRET_KEY` with no fallback. Demo user passwords are randomly generated per-run and printed once, never stored in git | `.env`/secret files are gitignored, but no secret-scanning pre-commit hook is configured |
| Username enumeration via login response timing | `login()` (`app/api/routers/auth.py`) always runs a bcrypt verification, even when the username doesn't exist, against a fixed dummy hash (`app/core/security.py::_DUMMY_PASSWORD_HASH`) so an unknown-username request costs the same as a known-username/wrong-password one; covered by `tests/test_api.py::test_login_rejects_unknown_username_without_erroring` | Only response *time* is equalized — response content already correctly returns the same 401 for both cases |

## Explicit non-mitigations (out of scope by design)
- QuantumShield does not scan real production infrastructure, so
  network-level attack surface against real systems is not a concern in
  the current lab-only scope.
- No production TLS termination happens inside this platform — the
  `CryptoProvider` abstraction never handles a real network handshake, so
  classic TLS implementation vulnerabilities (downgrade attacks, etc.) are
  not in scope for this codebase.
